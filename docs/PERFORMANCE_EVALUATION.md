# Performance evaluation and static baseline

This guide describes the current Ubuntu measurement and preserves the distinction from earlier historical data. See CURRENT_PERFORMANCE.md for the generated current results and RUNTIME_SOURCE_MANIFEST.json for the tested Python source identity.

## Question and measurement boundaries

Compare the protected service TCP transaction with dynamically installed
authentication-driven access and with a preinstalled static grant. Both modes
must use the same source, service, switch and VM environment. In audit_live.py
the benchmark source is root management 10.0.0.254 and the service is .4:8080.

- login_ms measures the authentication exchange, authenticated control request,
  switch confirmation and scheduling.
- service_rtt_ms includes TCP connection setup, request and application response.
  It is not raw propagation delay.
- login_to_access_ms spans login through the service response, before logout.
- Static login/total fields are blank, because that mode does not authenticate.
- A dynamic row is recorded only after successful access and confirmed logout.

Only service_rtt_ms is directly comparable across modes. Dynamic login-to-access
versus static service time compares different work and must not be presented as
a like-for-like speed ranking. The static grant has a dedicated cookie, specific
source/service match and finite timeout; the runner removes it in finally.

## Interpretation and limits

An ordered batch of 20 dynamic followed by 20 static trials is sensitive to VM
scheduling, load and cache effects. It does not establish causation or universal
performance superiority. Further randomized/repeated batches can strengthen the
analysis but are not a separately specified rubric requirement. Do not make
throughput/iperf or physical-network claims without retained command/output.

The packaged current CSV and generated summary are actual reviewed Ubuntu results, dated and linked to the measured source hashes. Further batches were not taken to select a favorable result.

The current batch contains six dynamic service observations above 1000 ms. Dynamic service mean is 309.6386 ms and median is 1.4515 ms; static mean is 1.2762 ms and median is 1.1660 ms. The long tail strongly affects the dynamic mean. No packet-level capture establishes the cause of those delays, and this ordered VM batch cannot isolate a causal SDN/HMAC overhead. All six remain in the data and report.
